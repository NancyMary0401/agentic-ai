01 1. First: What exactly is orchestration? ⌄

Orchestration is the mechanism that controls the workflow.

It answers:

Who runs? When do they run? What data do they receive? What happens after they finish? When does the workflow stop?

Suppose you have:

Research Agent


Comparison Agent


Writer Agent


Reviewer Agent

Just defining those four agents doesn't create a working system.

Something has to coordinate:

Which agent starts?



What does Research Agent receive?



Where does its result go?



Can two agents run simultaneously?



What if one fails?



Does Writer run before Comparison finishes?



Who decides whether Reviewer should send it back?



When is the workflow complete?

That responsibility is orchestration.

🧠 Memory:

Orchestration = WHO + WHEN + WHAT NEXT

03 3. Step 1 — User sends the request ⌄

At this point nothing magical has happened.

05 5. Step 3 — Create workflow state ⌄

This is extremely important.

The orchestrator generally needs to maintain state for the current run.

Conceptually:

{


  "user_request": "Research electric vehicles...",


  "research": null,


  "market_data": null,


  "comparison": null,


  "draft": null,


  "review_status": null,


  "final_answer": null


}

Think of this as the workflow's shared notebook.

Initially:

research       = EMPTY


market_data    = EMPTY


comparison     = EMPTY


draft          = EMPTY


review_status  = EMPTY

As agents execute, the state evolves.

🧠

Agents = workers

Orchestrator = manager

State = shared project file

06 6. Step 4 — Construct the Supervisor's model input ⌄

Now we finally reach the LLM level.

The model doesn't receive only:

"Research electric vehicles..."

The application constructs a context containing things such as:

SYSTEM INSTRUCTIONS



You are the supervisor of an EV research system.



Available specialists:



1. Research Agent


   Use for general EV research.



2. Market Agent


   Use for current market information.



3. Comparison Agent


   Use when information is available


   and products need comparison.



4. Writer Agent


   Use to produce the report.



USER



Research electric vehicles, compare Tesla and BYD,


and create a short report with the latest information.

Depending on the implementation, the available agents may be represented to the model as tools/handoffs with schemas, rather than just prose descriptions.

07 7. Now comes tokenization ⌄

Here's the important distinction.

The LLM doesn't internally process your sentence as a Java/Python string.

Before inference, text is encoded into tokens.

Simplified example:

"Research electric vehicles and compare Tesla and BYD"

could conceptually become pieces like:

"Research"


" electric"


" vehicles"


" and"


" compare"


" Tesla"


" and"


" BY"


"D"

That's only an illustration; actual token boundaries depend on the model's tokenizer.

Those tokens map to integer token IDs:

Token text           Token ID



Research       →     48123


 electric      →      7291


 vehicles      →     16532


 ...

Conceptually:

Text


 ↓


Tokenizer


 ↓


Token IDs


 ↓


Model
08 8. Tokens become vectors ⌄

Each token ID is mapped to an embedding vector.

Conceptually:

"Tesla"


   ↓


Token ID


   ↓


Embedding


   ↓


[0.17, -0.82, 0.44, 0.09, ...]

The actual vectors are high-dimensional numerical representations.

So:

Tokens


   ↓


Embeddings


   ↓


Transformer layers


   ↓


Contextual representations
09 9. Transformer processes the context ⌄

Through its transformer architecture, the model processes relationships among tokens in context.

It can relate concepts such as:

"compare"


    ↕


Tesla


    ↕


BYD


    ↕


latest information


    ↕


research

At a simplified level, the model is repeatedly computing a probability distribution for what token should come next.

10 10. The supervisor needs to choose an action ⌄

Here's where agentic behavior emerges from the surrounding runtime.

The model may determine:

I need EV research first.

But it doesn't have to output that as ordinary prose.

It can produce a structured tool call.

Conceptually:

{


  "tool": "research_agent",


  "arguments": {


    "topic": "current EV technology and Tesla/BYD"


  }


}

The critical point:

### The LLM itself isn't directly launching another Python process.

It generates an output indicating:

Call this tool/agent with these arguments.

The agent runtime/orchestrator interprets that output and performs the actual invocation.

This separation is extremely important.

LLM


 ↓


"I want Research Agent"


 ↓


Runtime / Orchestrator


 ↓


Actually invokes Research Agent
11 11. Now Research Agent gets its own context ⌄

The Research Agent can have a completely different system prompt.

SYSTEM:



You are an EV Research Agent.



Your responsibility is to gather factual information

Use web search when current information is required.



Do not write the final report.

Then it receives the delegated task:

16 16. Meanwhile — Parallel orchestration ⌄

Remember the Market Agent?

It may not depend on Research Agent.

Therefore the orchestrator can execute:

Supervisor


                  ↓


         ┌────────┴────────┐


         ↓                 ↓


   Research Agent      Market Agent


         ↓                 ↓


      Web Tool          Market Tool


         ↓                 ↓


      Result             Result

In Python this could be implemented with asynchronous concurrency such as asyncio.gather; in JavaScript, analogous workflows commonly use Promise.all.

17 17. How does the system know what runs next? ⌄

There are two major approaches.

18 18. Type 1 — Code-driven orchestration ⌄

You explicitly define:

START


 ↓


Research + Market


 ↓


Comparison


 ↓


Writer


 ↓


Reviewer


 ↓


END

Your application determines the transitions.

Conceptually:

research, market = await run_parallel(...)



comparison = await comparison_agent(


    research,


    market


)



draft = await writer_agent(comparison)



review = await reviewer_agent(draft)

Very deterministic.

19 19. Type 2 — LLM-driven orchestration ⌄

Instead, you tell the Supervisor:

Available agents:



Research


Market


Comparison


Writer


Reviewer



Determine what should happen next.

Then after Research finishes, the Supervisor LLM may receive:

User goal


+


Current state


+


Available agents

and choose:

{


  "next_agent": "comparison_agent"


}

So:

State


 ↓


Supervisor LLM


 ↓


Decision


 ↓


Runtime


 ↓


Next Agent

That's dynamic routing.

20 20. Type 3 — Hybrid orchestration ⭐ ⌄

This is often a strong production design.

Some decisions should be deterministic.

Some decisions benefit from LLM reasoning.

For example:

Request


                      ↓


                Supervisor LLM


                      ↓


              Understand Intent


                      ↓


          ┌───────────┴───────────┐


          ↓                       ↓


     Research Agent          Market Agent


          └───────────┬───────────┘


                      ↓


              CODE-DEFINED RULE


        "Wait until BOTH complete"


                      ↓


               Comparison Agent


                      ↓


                  Writer


                      ↓


                 Reviewer


                      ↓


                ┌─────┴─────┐


                ↓           ↓


              PASS         FAIL


                ↓           ↓


              END        Writer


                             ↑


                             │


                          feedback

You don't need an LLM to reason:

"Did both required tasks finish?"

Code can determine that reliably.

But you might use an LLM for:

"What kind of research is necessary?"

That is a more semantic decision.

24 24. Handoff orchestration ⌄

This is different.

Suppose:

User:


"I need help writing Python."

Triage Agent says:

Python Specialist should handle this.

Then:

User


 ↓


Triage Agent


 ↓


HANDOFF


 ↓


Python Agent


 ↓


Python Agent continues conversation

The Python Agent takes over.

Control doesn't necessarily return to the triage agent.

### Manager vs Handoff

MANAGER



User


 ↓


Manager


 ↓


Specialist


 ↓


Manager


 ↓


User

versus:

HANDOFF



User


 ↓


Triage


 ↓


Specialist


 ↓


User

This is an excellent interview distinction.

25 25. Hierarchical orchestration ⌄

      Research Supervisor         Report Supervisor


            ↓                           ↓


       ┌────┴────┐                ┌─────┴─────┐

Now delegation happens at multiple levels.

Useful when you have many specialized capabilities.

26 26. Agent-to-Agent communication ⌄

There's another architecture:

Agent A


   ↓


Agent B


   ↓


Agent C

Agents can communicate/delegate without one central manager controlling every interaction.

For interoperability between independently implemented agents, the A2A protocol is one current standard aimed at agent-to-agent discovery, delegation, and result exchange. Its documentation distinguishes A2A from MCP: broadly, A2A is agent↔agent, while MCP is agent↔tools/resources.

Don't mix those concepts up.

30 30. Now orchestration creates a LOOP ⌄

This is another major orchestration pattern:

Writer


  ↓


Reviewer


  ↓


PASS? ───── YES ───→ END


  │


  NO


  ↓


Writer


  ↑


feedback

So orchestration isn't always:

A → B → C

It can be:

A → B → A → B → A → B

until some condition is met.

But production systems should normally have limits such as:

max_iterations = 3

Otherwise you risk:

Writer → Reviewer → Writer → Reviewer → ...

and runaway latency/cost.

34 34. One correction that will make your interview answer stronger ⌄

Avoid saying:

"The LLM executes the API."

More accurately:

"The model selects or emits a tool call, and the agent runtime executes the corresponding function/API and returns the tool result to the model."

Similarly, avoid:

"The agent automatically knows which agent to call."

Say:

"Depending on the orchestration design, routing can be determined by application code, by an LLM supervisor through tool/handoff selection, or by a hybrid of both."

Those distinctions show that you understand what's actually happening.

35 35. The architecture in one sentence ⌄

If an interviewer says:

“Explain the end-to-end flow of a multi-agent application.”

You can answer:

“The user request enters the application through an API layer and is passed to the agent runtime. Relevant instructions, conversation context, workflow state, and available tool or agent schemas are assembled into the model context and tokenized. The supervisor model can then select an appropriate specialist through a tool call or handoff, or routing can be controlled deterministically by application code. Specialist agents may call external tools, whose results are added back into their context for further model inference. Their outputs update workflow state, and the orchestrator coordinates subsequent agents sequentially, in parallel, or through conditional loops. Once completion and validation conditions are satisfied, the final model output is generated token by token and streamed or returned through the backend to the user.”

That's the complete mental model I want you to have.
